# 客户端下载与分发架构

> **适用范围**：公开部署环境下用户端 Web、Android 与 iOS 客户端的托管、更新校验与平台合规分发边界。

## 1. 多端统一工程与分阶段交付原则

正式用户端（`apps/client_flutter/`）使用同一套源码产出三端应用，按平台准入条件分层提供服务：

1. **Flutter Web（零门槛默认入口）**：随 `make bundle` 编译进发布包 `apps/client-web/`，直接由用户端 HTTPS 站点同源托管，桌面浏览器、Android 与 iOS Safari 均可即开即用，无应用商店审核或证书签名阻塞。
2. **自有下载站托管机制**：移动端原生安装包通过部署者自行配置的独立 HTTPS 下载站分发，下载站仅承担静态安装包与更新说明托管，不介入认证、任务调度或支付入账。主服务能力接口仅在实际配置了下载站地址时返回下载入口，未配置时客户端隐藏相关链接，不展示无效占位按钮。

## 2. Android 客户端签名与自托管分发

- **服务连接解耦**：公开或通用构建的 APK 默认不内置特定服务器域名，用户首次打开应用在 `/connect` 页面输入部署方提供的 HTTPS 地址并通过 `/api/v1/capabilities` 探针核验后保存；部署方也可在自建构建时通过 `--dart-define=API_BASE_URL=https://learn.example.com/api/v1/` 注入默认地址。
- **发布签名连续性**：本地 `flutter build apk --debug` 仅用于开发联调，且 `build-bundle.sh` 明确禁止将调试包混入服务端发布归档。面向最终用户分发时，部署者必须使用独立离线保管的正式 Keystore 构建 `release` 签名包，并在后续版本升级中保持相同签名证书，依托 Android 系统标准的“允许安装未知应用”授权流完成安装与覆盖更新。
- **版本清单校验**：下载站配套提供包含应用包名、语义化版本号、要求最低服务端 API 版本、包体积与文件 `SHA-256` 摘要的元数据清单，供用户与客户端核验完整性。

## 3. iOS / iPadOS 分发合规边界

Apple 生态对 iOS 原生安装包分发实施严格的硬件签名与地区政策限制：

- **禁止违规直装承诺**：仅将未签名或普通开发签名的 `.ipa` 上传至网页并不能让普通 iOS 设备直接安装；Apple Developer Enterprise Program（企业证书）按官方协议仅限组织内部员工自有设备使用，不得用于向公众分发；Apple 官方 Web Distribution 仅面向满足特定资质审核与欧盟地区系统条件的应用开放。
- **标准推荐路径**：在部署方未取得合规 App Store 上架、TestFlight 测试名额或符合目标地区法规的正式分发资格前，iOS 与 iPadOS 用户统一使用同源托管的 **Flutter Web（支持添加到主屏幕全屏访问）**，获得完整的课程同步、学习安排、实时进度与钱包体验。

## 4. 客户端生命周期与支付回跳边界

- **纯展示与控制终端**：移动端 App 在切入系统后台或进程被系统回收期间**不承担任何本地学习任务执行**，全部调度、原生 HTTP 上报与平台二次核验均在服务端持续完成；App 回到前台时自动重拉最新权威快照并恢复 SSE 连接。
- **收银台回跳零信任**：移动端拉起外部浏览器或支付渠道完成 ZPay 付款后跳回 App 时，客户端仅向主服务轮询对应充值订单的最新入账状态，实际余额增加完全取决于服务端管理口验签回调与主动对账事务。若未来接入特定应用商店内分发渠道，支付方式须按对应商店的数字商品结算政策另行适配。
