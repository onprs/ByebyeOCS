# 钱包、双轨计量、ZPay 支付与对账架构

> **适用范围**：财务与计费核心架构规范，对应 `server/internal/ledger`、`server/internal/payments` 及主库账本表结构。

## 1. 复式记账账本与微元整数定价

### 1.1 人民币整数分不可变复式账本

系统严禁使用浮点数存储或计算金额，一切资金余额与变动均以**人民币整数分（`int64`）**记账，并通过 JSON 十进制字符串（如 `"3000"` 表示 `30.00` 元）传输：

- **借贷平衡不变量**：每次资金变动必须在单个 PostgreSQL 事务内写入一条具有全局唯一业务幂等键的 `ledger_journals` 及至少两条带符号的 `ledger_postings`，同一分录下所有 `postings` 的金额代数和强制等于 `0`。已提交的 `journals` 与 `postings` 永不执行 `UPDATE` 或 `DELETE`，冲正与退款一律追加反向新分录。
- **受检余额缓存**：`wallets` 表上的 `available_minor`（可用余额）与 `held_minor`（冻结预占）在同一账本事务中按固定锁顺序原子更新并校验非负约束，随时可由历史 `postings` 完整对账重建。

| 典型业务动作 | 复式分录方向（整数分） | 幂等业务唯一键构成 |
| --- | --- | --- |
| 渠道充值入账 | 用户可用 `+M`；渠道清算 `-M` | `recharge:<provider>:<merchant_id>:<channel_trade_no>` |
| 任务/查题冻结预占 | 用户可用 `-H`；用户预占 `+H` | `hold:<charge_intent_id>:<hold_generation>` |
| 用量确认捕获结算 | 用户预占 `-C`；服务收入 `+C` | `capture:<charge_intent_id>:<settlement_unit>` |
| 释放未消费预占 | 用户预占 `-R`；用户可用 `+R` | `release:<hold_id>:<release_unit>` |
| 服务消费退回钱包 | 服务收入 `-S`；用户可用 `+S` | `service_refund:<original_charge_id>:<refund_id>` |
| 渠道原路退款预留 | 用户可用 `-P`；退款应付 `+P` | `payout_reserve:<refund_id>` |
| 渠道原路退款完成 | 退款应付 `-P`；渠道清算 `+P` | `payout_complete:<refund_id>` |
| 管理员人工调账 | 用户可用 `±A`；调账对冲账户 `∓A` | `admin_adjust:<idempotency_key>`（绑定管理员与理由） |

### 1.2 微元单价与整数商余舍入（迁移 21）

为精确表达大模型每千/百万 token 的细粒度费率与任务点单价，系统内部单价统一采用 **微元（`1 人民币分 = 10,000 微元`，`1 元 = 1,000,000 微元`）** 存储。结算折算为整数分时采用纯 64 位整数商余算法（防乘法溢出），支持管理员配置三种确定性舍入策略：`ceil`（向上取整，不足 1 分且大于 0 微元按 1 分计）、`floor`（向下取整）与 `half_up`（标准四舍五入）。

## 2. 主服务与题库双轨独立计量

1. **主服务计量（平台已确认的有效任务点）**：
   - 计量单位严格定义为**首次由新鲜独立平台查询确认完成的带编号有效任务点**。
   - 普通无编号附件、执行前已在平台预完成的任务点、排队等待、执行器观察进度、失败重试、暂停取消或平台关闭项均不产生计费事件；同一稳定任务点跨多个安排重叠绑定或多次重试，全局唯一约束保证最多只结算一次。
2. **独立题库计量（服务端确认的模型 Token）**：
   - 题库价格版本在 `/panel/` 只追加发布，主平台在创建每次查询时将当时的公开条目费率（输入、输出、缓存读取、缓存创建微元单价）冻结进查询行，后续面板改价绝不追溯影响在途或历史查询。
   - `cache_first` 命中精确缓存时 token 消耗为 `0`，不扣取模型费；当启用视觉转述模型时，汇总 `caption` 与 `answer` 槽位各自真实消耗计费。
   - **安全免扣边界**：当部署配置或管理端关闭收费总开关、目标条目处于 `unpriced` 未定价状态、或上游返回 `usage_incomplete` / `request_unknown` 时，系统自动跳过扣费并保留完整用量记录供后台核对。

## 3. ZPay 支付集成、主动对账与双类退款分离

系统对接已确认的支付渠道 **ZPay（`https://zpayz.cn`）**，生产模式下启用支付或自动扣费强制要求 `operations.require_fresh_backup: true` 且最近异机恢复点未超过 `15 分钟`：

- **下单与同步回跳隔离**：`notify_url` 与 `return_url` 在配置加载与客户端调用双层拦截查询参数（遵循 ZPay 接口规范）。用户在收银台支付后的浏览器/App 同步回跳仅用于定位并轮询本地订单状态，**无权修改订单支付标志或钱包余额**。
- **管理口回调 Inbox 与验签**：异步通知唯一内部入口为管理监听上的 `POST /payments/callbacks/zpay`。处理器校验商户号、签名（常数时间比对）、订单归属与精确元转分金额后，先写入幂等回调 Inbox；若同一订单收到重复 `TRADE_SUCCESS` 通知直接幂等返回 `success`；若发现异常第二笔不同渠道流水号付款，单独记入异常待复核台账而不静默吞没资金。
- **主动查单对账**：针对网络抖动漏通知、已付款未入账及指定关闭订单，管理端 `/finance` 支持调用 ZPay 订单查询接口主动拉取渠道真实状态完成补偿入账。
- **两类退款严格分离**：正常到账充值余额原则上不开放用户自助提现；后台复核处理争议时，明确区分**服务消费退回平台钱包**（冲减服务收入、增加可用余额，不走外部支付网关）与**充值原路退回支付渠道**（先冻结扣减可用余额转入退款应付，调用渠道退款确认后再核销清算；尚未发出的 `requested` 退款若失败可安全回退释放预留资金）。
